# Google Contacts: расширенный импорт и кнопка «Обновить в Google»

Дата исследования: 27 октября 2026. Репозиторий: kirei4ik/pingcrm, main на коммите `bff47390515835c01f4b4aae50284ab4f02dbaea`.
Задача: получать контакты и календарь без Gmail, полноценно читать карточки Google и вручную дополнять Google Contacts данными PingCRM. Автоматическая обратная синхронизация не требуется.

## Вывод

Доработка технически реализуема. Рекомендованный подход — расширенный односторонний импорт Google → PingCRM и отдельная операция записи по кнопке: **выбрать Google-аккаунт и карточку → прочитать её актуальное состояние → показать изменения → подтвердить выбранные поля → записать**.

Это не небольшое изменение OAuth scopes. Основная работа — корректная привязка карточек к Google-аккаунтам, сохранение многозначных полей и защита от конфликтов. Внедрять стоит двумя этапами: сначала исправить импорт и связи, затем включать ручную запись. Нельзя обещать отсутствие регрессий до тестирования.

Приложение, репозиторий на GitHub, Google-аккаунты и Coolify в рамках этого исследования не менялись. Сохранены только исследовательские документы.

## 1. Что проверено

- Просмотрены адаптер People API, задачи импорта, OAuth callback, модели контактов и GoogleAccount, защита ручных правок, слияние дублей, API и интерфейс контакта.
- Хеши 13 ключевых локальных исходников сопоставлены с деревом указанного коммита GitHub: различий нет. Локальные изменения Compose от предыдущей работы не использовались как доказательство состояния приложения.
- Выполнен изолированный эксперимент с фактической функцией `_extract_contact_fields` и синтетической полной Google-карточкой. Он подтвердил потерю birthdays, biographies, addresses, urls и userDefined; типы email/телефонов также не сохраняются. Реальные пользовательские данные не читались.
- Изучены имеющиеся тесты; они в этой исследовательской задаче не запускались. Полный backend-набор требует PostgreSQL, а проверка реального Google — отдельного тестового аккаунта.
- Контракт Google People API проверен по официальной документации. Инженерные предложения ниже отделены от подтверждённого текущего поведения.

## 2. Почему карточка импортируется неполностью

[`google_contacts.py`](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/integrations/google_contacts.py#L47) запрашивает в `personFields` только `names,emailAddresses,phoneNumbers,organizations`.
Маппер берёт первый элемент имени и организации, превращает email и телефоны в простые строки. Он не читает дни рождения, заметки, адреса, фото, ссылки и дополнительные поля.

[`_sync_google_contacts`](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/services/task_jobs/google.py#L34) заполняет имя, фамилию, компанию и должность существующего контакта только если соответствующее поле пустое. Новые телефоны дописываются, но дополнительные email к уже существующему контакту не объединяются в этой ветке. Поэтому обычная повторная синхронизация не исправляет старое заполненное имя.

В том же коде есть эвристика разделения имени и компании. Она меняет `fields["full_name"]`, но создание/обновление использует сохранённый ранее `raw_name`. Это несогласованность текущего кода, которую нужно покрыть отдельным регрессионным тестом. Она не доказывает происхождение имени конкретного контакта со скриншота.

Существующий [`sync_set_field`](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/services/sync_utils.py#L18) умеет учитывать `user_edited_fields`. Google-импорт сейчас использует собственные присваивания и эту функцию не вызывает. В [API ручного редактирования](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/api/contacts_routes/crud.py) отмечаются поля, которые пользователь менял сам.

## 3. Что значит «полная карточка»

«Не терять данные Google» и «показать все данные в интерфейсе PingCRM» — разные объёмы работы. Предлагается сохранять структурированный снимок полученной Google-карточки, а в обычные поля PingCRM переносить поддерживаемые значения.

| Данные Google | Текущее хранение PingCRM | Предлагаемая первая версия |
| --- | --- | --- |
| Имя, фамилия | Есть | Выбирать основное значение по metadata; обновлять с учётом источника и ручных правок |
| День рождения | Есть строковое birthday | Импортировать YYYY-MM-DD или MM-DD без выдуманного года |
| Телефоны, email | Массивы строк | Объединять значения; в снимке сохранять типы, метки и основное значение |
| Компания, должность | По одному полю | Основную организацию отображать; остальные сохранять в снимке |
| Заметка/биография Google | Есть общие notes | Не смешивать молча с личными CRM-заметками; хранить Google-значение отдельно |
| Telegram, LinkedIn и другие ссылки | Есть отдельные социальные поля | Сопоставлять известные ссылки; сохранять произвольные ссылки структурированно |
| Адреса | Есть только общее location | Сохранять полный адрес и тип отдельно; не превращать автоматически все адреса в одну строку |
| Фото | Есть avatar_url | Импорт можно добавить; отправку фото отложить |
| Дополнительные поля | Нет универсальной модели карточки | Сохранять userDefined с ключами и значениями; отображение добавить отдельно |

Поддерживаемые группы полей, primary metadata и даты описаны в [Person](https://developers.google.com/people/api/rest/v1/people); чтение — в [connections.list](https://developers.google.com/people/api/rest/v1/people.connections/list).
Большинство групп — массивы: выбор просто первого элемента ненадёжен. Снимок должен хранить только нужные контактные данные и не содержать OAuth-токены. Доступ к нему ограничивается владельцем CRM-контакта.

Для новых импортированных карточек Google может быть основным источником имени и дня рождения. Для существующих карточек безопаснее один раз показать конфликты и предложить «взять из Google», сохранив ручные правки. Нужен снимок последнего импортированного значения по полям: он отличает изменение источника от правки пользователя. Одна глобальная метка `source="google"` этого не решает.

## 4. Обязательные изменения привязок

В [Contact](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/models/contact.py#L17) есть только одно `google_resource_name`. [GoogleAccount](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/models/google_account.py#L12) поддерживает несколько подключённых аккаунтов, но контакт с конкретным аккаунтом не связан.

Рекомендуется отдельная таблица связей, например `GoogleContactLink`:

- CRM contact_id;
- GoogleAccount.id, определяющий конкретные OAuth credentials;
- resource_name и metadata контактного источника Google;
- снимок последнего чтения, source etag, время чтения и состояние связи.

Одна карточка PingCRM может иметь несколько связей, если один человек есть в нескольких адресных книгах. Связь уникальна внутри Google-аккаунта. На каждом чтении и записи сервер проверяет владельца контакта и владельца GoogleAccount; email контакта не используется как единственное доказательство тождества.

Существующее одиночное поле нельзя автоматически разнести по аккаунтам при неоднозначности. Для одного аккаунта связь можно проверить чтением Google; при нескольких — нужна перепроверка и, при конфликте, выбор пользователя. Если карточка отсутствует, не создавать новую автоматически.

Обязательные смежные исправления:

1. **Частичный сбой и архивирование.** Сейчас `seen_resource_names` собирается глобально, а после успешного чтения хотя бы одного аккаунта все отсутствующие связанные контакты пользователя могут архивироваться. Если второй аккаунт не прочитан, его карточки тоже могут попасть в эту выборку. Политика отсутствия должна работать отдельно по успешно полностью прочитанному аккаунту; для первой версии разумно отмечать «не найден в источнике», не архивировать весь CRM-контакт автоматически.
2. **Слияние дублей.** [`merge_contacts`](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/services/identity_resolution.py#L178) удаляет вторую карточку, но список переносимых скалярных полей не содержит google_resource_name, birthday, avatar_url и user_edited_fields. Новые связи и снимки должны переноситься на оставшуюся карточку; старые поля тоже требуют явной политики объединения.
3. **OAuth подключения дополнительного аккаунта.** [Callback](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/api/auth.py#L227) проверяет владельца state, но далее выбирает/создаёт CRM User по email Google и выдаёт токен этого User. Подключение аккаунта с другим email может переключить пользователя и привязать аккаунт к другой CRM-записи. Для connect-flow нужно привязывать GoogleAccount к инициировавшему caller; вход и подключение должны быть разными сценариями. Это подтверждённая структура кода; её фактическое проявление требует интеграционного теста.

Эти изменения важнее красивой кнопки: без них нельзя надёжно выбрать адресную книгу для записи.

## 5. Как должна работать кнопка «Обновить в Google»

Предлагаемый интерфейс карточки:

1. «Обновить в Google».
2. Выбор подключённого аккаунта и его связанной Google-карточки. Если связь одна, показывать её явно без лишнего выбора.
3. Таблица «Поле / Сейчас в Google / Предлагается из PingCRM / Действие».
4. По умолчанию выбраны только новые данные и заполнение пустых полей.
5. Замена заполненного имени, компании или дня рождения требует отдельного выбора; удаления в первой версии нет.
6. «Применить выбранное» и итоговый список выполненных изменений.

Пример: в Google есть один рабочий телефон, в PingCRM появился дополнительный мобильный и Telegram. Предложение добавляет мобильный и ссылку t.me, сохраняя рабочий телефон, его метку и все остальные поля Google.

В первую версию включить: телефоны, email, компанию/должность, выбранное имя, день рождения и ссылки на профили. Telegram лучше представлять как ссылку `https://t.me/username`; LinkedIn — как URL профиля. Не переносить автоматически переписку, relationship_score, внутренние теги, AI-выводы и приватные заметки. Экспорт заметок — отдельный явный выбор позже.

Без подтверждённой связи показывать «контакт не связан с Google». Поиск кандидатов можно добавить, но не выбирать автоматически только по совпадению имени. Создание Google-контакта — отдельная будущая команда, вне кнопки обновления.

## 6. Контракт Google и защита от потери данных

Запись через [people.updateContact](https://developers.google.com/people/api/rest/v1/people/updateContact) требует scope `contacts`, source metadata и актуального etag. Маска `updatePersonFields` заменяет выбранные группы целиком. Поэтому сервер читает актуальную карточку и объединяет весь массив телефонов/email/ссылок с выбранными добавлениями; не отправляет неполный ContactResponse как новую карточку.

При изменении Google-карточки после предпросмотра возникает конфликт версии (Google документирует 400 failedPrecondition). Нужны новое чтение и новый предпросмотр, а не слепой повтор PATCH. Также нужно проверять, что карточка PingCRM не изменилась после предпросмотра.

Предлагаемый серверный контракт:

- POST preview: read-only по отношению к Google; строит изменения из разрешённых полей, возвращает короткоживущий preview_id.
- POST apply: принимает preview_id и выбранные действия; проверяет владельца, срок, версии, согласованную связь и список разрешённых полей.
- Повторный apply того же preview не создаёт повторных добавлений. Таймаут после отправки в Google означает «результат неизвестен»: сначала перечитать карточку, затем решать, что осталось выполнить.
- Журналировать аккаунт, Google-карточку, выбранные поля, предыдущие/новые значения и результат. Не писать access/refresh tokens в журнал.
- Сохранять результат ответа Google и обновлять снимок источника; записи для одного Google-аккаунта выполнять последовательно.
- Не обещать транзакционный откат между Google и PostgreSQL. Восстановление предыдущих значений — отдельная проверяемая операция с новым etag.

Путь нового API можно разместить отдельным подроутером контакта. Рядом уже есть меню [header-actions-menu.tsx](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/frontend/src/app/contacts/%5Bid%5D/_components/header-actions-menu.tsx), но кнопке потребуются новый диалог, DTO preview/apply и обновление генерируемых OpenAPI-типов. Информация о наличии связи должна появиться в API ответа контакта; сейчас ContactResponse её не отдаёт.

## 7. Google без доступа к почте

[`google_auth.py`](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/integrations/google_auth.py#L11) сейчас объединяет contacts.readonly, calendar.readonly, gmail.readonly и gmail.send.
Для чтения достаточно контактов, календаря и базового профиля. Для ручной записи понадобится `https://www.googleapis.com/auth/contacts`; предпочтительно дополнительное согласие при первом нажатии кнопки и проверка реально выданных прав. Календарь оставить read-only. [Google Calendar scopes](https://developers.google.com/workspace/calendar/api/auth).

Просто удалить Gmail scopes недостаточно:

- [handleGoogleSyncAll](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/frontend/src/app/settings/_hooks/use-settings-controller.ts#L289) явно запускает три операции, включая Gmail;
- [Celery beat](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/core/celery_app.py) запускает Gmail-sync и отправку подготовительных писем к встречам;
- остаётся ручной [API чтения писем конкретного контакта](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/api/contacts_routes/sync.py#L241);
- настройки и история Google в UI частично привязаны к `platform="gmail"`;
- старые refresh tokens могут сохранять ранее выданные Gmail-права.

Нужно прекратить эти вызовы, отправку писем и запрос почтовых разрешений в выбранном режиме. Существующую историю не удалять без отдельного решения. Для отказа от прежнего доступа к почте пользователь отзывает старое разрешение и подключает Google заново. Изменение константы scopes не расширяет и не очищает старый токен автоматически; `include_granted_scopes=true` может включить старые права. [OAuth web-server flow](https://developers.google.com/identity/protocols/oauth2/web-server).

## 8. Тестирование, которое действительно снижает риск

Имеется база тестов: [test_google_contacts_sync](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/tests/test_google_contacts_sync.py), [test_task_jobs_google](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/tests/test_task_jobs_google.py), [test_auth_google](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/tests/test_auth_google.py), тесты календаря и интерфейса контакта. Некоторые тесты фиксируют нынешнее «не заменять заполненные поля»; новую политику нужно задавать явно. Наличие тестов не означает, что предлагаемая запись уже проверена.

Нужные сценарии:

1. Полная синтетическая Google-карточка: день рождения с/без года, несколько email/телефонов с метками, несколько компаний, адреса, заметки и неизвестные дополнительные поля.
2. Повторный импорт без дублей; изменение имени в Google; защита ручной правки и намеренно очищенного поля в CRM.
3. Два Google-аккаунта, один контакт в обеих книгах; отказ одного аккаунта без архивирования другого; неоднозначные legacy-связи.
4. Слияние CRM-дублей сохраняет связи с обоими Google-аккаунтами, день рождения и ручные правки.
5. Добавить один телефон, сохранив остальные и их типы. Невыбранные поля и приватные заметки не отправляются.
6. Повторный apply; истёкший preview; изменение CRM или Google после preview; Google timeout после фактического успеха.
7. Read-only/revoked token, чужой CRM contact, чужой GoogleAccount, недоступный контакт Google и отсутствие CONTACT source.
8. Подключение второго Google-аккаунта не создаёт нового CRM-пользователя и не меняет текущую сессию.
9. OAuth и Sync в режиме Contacts+Calendar не запрашивают и не вызывают Gmail. Календарь продолжает работать.
10. Миграция на копии базы без удаления старых связей, затем smoke-test на отдельном Google-аккаунте с подготовленными контактами.

## 9. Этапы внедрения и границы первой версии

**Этап A — база надёжного импорта:** связи GoogleAccount↔Contact, снимки источников, фиксация OAuth connect-flow и слияния, защита при частичном чтении; расширение personFields/маппера; источники полей и предпросмотр конфликтов имени. В первой волне отображать имя, день рождения, телефоны, email, компанию, заметку и ссылки; остальные поля сохранять без потери в структуре Google-деталей.

**Этап B — ручная запись:** отдельный API preview/apply, diff UI, дополнительное разрешение contacts, защита версий и журнал операций. Включить для одного тестового аккаунта, затем одного реального контакта после проверки.

**Этап C — дополнительные удобства:** произвольные дополнительные поля в UI, фото, явное создание нового Google-контакта. Не включать в минимальный объём и не делать автоматическую двустороннюю запись.

Первый импорт после миграции — полный, без массовой замены заполненных полей и без автоматического архивирования. До миграции сделать резервную копию PostgreSQL. Во время проверки приоритетов не использовать реальные Google Contacts как тестовый набор.

Оценка: этап A — умеренная сложность с повышенным вниманием к миграции связей; этап B — умеренная/повышенная из-за внешних записей. Кнопка существенно уменьшает риск неконтролируемых обновлений по сравнению с фоновым экспортом, но не отменяет требования к привязке, объединению массивов и версиям.

## 10. Критерии готовности

Можно включать функцию для обычного использования, когда:
- импорт показывает ожидаемые поля тестовой карточки и сохраняет остальные данные без потерь;
- целевой Google-аккаунт всегда известен и проверяется на сервере;
- предпросмотр отражает ровно то, что будет отправлено;
- проверены сохранность заполненных полей, повторное нажатие и конфликт версий;
- Gmail не вызывается, Calendar работает;
- выполнена проверка на копии БД и в тестовом Google-аккаунте.

До этих проверок утверждение «ничего не сломается» не обосновано. По результату чтения кода рекомендуемый путь реализации есть; гарантировать его поведение на текущих пользовательских данных пока нельзя.

## 11. Дополнение: счётчики, ярлыки и ссылка на карточку (27 октября 2026)

### Разница 616 Google / 646 PingCRM

Эти числа не доказывают наличие ровно 30 дублей. PingCRM объединяет контакты разных источников: Google Contacts, Telegram, импорт и ручное создание. В частности, `google_calendar.py::_find_or_create_contact` создаёт записи для участников встреч с `source="google_calendar"`, если их ещё нет в CRM. Источник: [Google Calendar adapter](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/integrations/google_calendar.py#L116).

Возможны также дубли: Google-импорт ищет существующую карточку по resourceName и email, но не делает сопоставление по телефону в этой ветке; потеря google_resource_name при слиянии, описанная выше, может мешать последующему сопоставлению. Это возможные механизмы, а не установленная причина чисел пользователя.

Нужна сверка конкретного Google-аккаунта: число полученных Google Person, число уникальных связей с CRM, число CRM-контактов без связи, неоднозначные/дублирующиеся связи и контакты прочих источников. Фильтр source не заменяет эту проверку: CRM-карточка может содержать сведения нескольких источников, сохраняя одно значение source. Во время сверки ничего не удалять и не объединять автоматически.

### Импорт ярлыков Google Contacts

Поддерживается People API. Список пользовательских ярлыков получается через [contactGroups.list](https://developers.google.com/people/api/rest/v1/contactGroups/list), принадлежность человека — через `memberships.contactGroupMembership.contactGroupResourceName` в [Person](https://developers.google.com/people/api/rest/v1/people). Для чтения достаточно contacts.readonly; members не заполняются непосредственно в ответе list групп. Нужно читать все страницы групп и memberships карточек.

Предлагается сохранить ярлыки источника отдельно от внутренних CRM-тегов: GoogleAccount + contactGroup resourceName + оригинальное name + связь с Person. Сохранять регистр, кириллицу, числовые префиксы и переименования по стабильному ID группы, а не по тексту. Текущая [нормализация tags](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/schemas/contact.py#L7) приводит строки к нижнему регистру, поэтому простая запись ярлыков в tags не обеспечивает точного отображения. Системные группы не показывать как пользовательские ярлыки. Добавить фильтр по Google-ярлыку и отображение на карточке.

Сумма чисел рядом с ярлыками не обязана совпадать с общим числом контактов: один человек может состоять в нескольких группах. Первая версия читает ярлыки; кнопка «Обновить в Google» не должна менять memberships без отдельного выбранного действия. При переименовании/снятии ярлыка в Google обновляется только его источник, а собственные теги CRM сохраняются.

### Кнопка «Открыть в Google Contacts»

Добавить можно при наличии проверенной связи с конкретной Google-карточкой. Показать имя/адрес целевого Google-аккаунта, а при нескольких связях — список. Ссылка открывается в новой вкладке и не даёт новых API-прав.

На скриншоте пользователя виден веб-маршрут `contacts.google.com/person/…`. Его формат и соответствие идентификаторов UI, CONTACT source и People resourceName нужно проверить на тестовом аккаунте. В исследованной официальной документации People API не найден гарантированный webUrl карточки или контракт преобразования resourceName в этот веб-адрес. Нельзя обещать правильную ссылку простой заменой `people/` на `person/` без проверки. Следует учесть аккаунт, выбранный в браузере Google; /u/0 не является надёжной привязкой к нужному аккаунту. Отсутствующая/неоднозначная связь не должна вести на случайную карточку.

Тесты дополнения: кириллица и регистр ярлыков, несколько memberships, переименование и удаление группы, несколько аккаунтов с одинаковыми названиями ярлыков, независимость CRM tags, точное открытие Google-карточки для контакта без email и с несколькими аккаунтами.

## 12. Проверка блока организаций

Наблюдение пользователя: список организаций показывает 0, хотя у многих CRM-контактов заполнено поле компании. Добавить в обязательный объём диагностики и регрессионных проверок первой версии.

### Найденное по коду

- Google-импорт записывает `Contact.company` и `title`, но не вызывает `auto_create_organization` и не устанавливает `organization_id`: [Google import](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/services/task_jobs/google.py#L134).
- Для автоматического создания и связи уже существует отдельный [organization_service](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/services/organization_service.py#L176). Он используется в других сценариях, включая создание/изменение контакта через API.
- [GET organizations](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/api/organizations.py#L143) показывает только организации, имеющие активные контакты с заполненным `organization_id`. Сам текст `company` не создаёт такую связь.
- В просмотренном [ORM listener](https://github.com/kirei4ik/pingcrm/blob/bff47390515835c01f4b4aae50284ab4f02dbaea/backend/app/models/listeners.py) реализован геокодинг, а универсального создания организации при заполнении company нет.

Эта разница в путях импорта хорошо объясняет наблюдаемый симптом; реальное состояние пользовательской базы и точное число отсутствующих связей не проверялись. Это кодовое обоснование вероятной причины, не завершённая диагностика конкретной базы.

### Что проверить и исправить при реализации

1. Сопоставить число активных контактов с непустым company, число из них с organization_id и число организаций, попадающих в API списка. Проверить поиск/фильтры интерфейса и отдельные права владельца.
2. Убедиться, что Google-импорт создаёт/находит организацию и привязывает контакт после определения company. Пустая компания не создаёт организацию; повторный импорт не создаёт дублей.
3. Подготовить одноразовое восстановление связей для уже импортированных контактов. Сначала показать перечень предполагаемых организаций/назначений; не объединять похожие, но разные названия автоматически.
4. Сохранять ручные назначения организаций и защищённые значения company. Изменение компании в Google должно проходить ту же политику источников и конфликтов, что имя.
5. Проверить нормализацию регистра и пробелов, одинаковые названия у разных CRM-пользователей, контакты без корпоративного email, работу на личных Gmail/Яндекс-адресах. Домен помогает сопоставлению, но не является обязательным для создания организации по названию.
6. Проверить правила видимости организаций без активных контактов, статистику, архивирование контактов и перенос organization_id при слиянии дублей.
7. Ошибка скачивания логотипа не должна терять организацию или срывать импорт контактов.

Критерий приёмки: на тестовом импорте контакта с компанией появляется одна связанная организация; повторный импорт не создаёт вторую; восстановление существующих записей наполняет список и не меняет ручные связи. Тестировать adapter/task → PostgreSQL → API списка → UI, а не только функцию создания организации отдельно.

Этот пункт — часть исследуемой доработки. Рабочая база не менялась, массовое создание организаций не запускалось.
